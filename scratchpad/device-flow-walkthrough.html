Reading the codebase

How the device flow actually moves through this code

Both apps are built the same way: five small layers that map directly onto the two HTTP calls Descope's device grant needs. This is a guided read of that shape — what each file is responsible for, and where the OAuth spec shows up in the code — before you look at pushing it anywhere.

1

The sequence, end to end

Two devices are involved, and they never talk to each other directly — Descope is the only thing both sides ever call. That's the whole idea of device flow: the TV/phone running this app has no keyboard worth typing a password into, so it hands the actual login off to whatever device the user approves from.

Five layers, one dependency chain

Every layer only knows about the one above it. Views hold a ViewModel; the ViewModel holds a Service; the Service reads Config and returns Models. Nothing reaches backward. That's why the same DeviceAuthService/DeviceAuthViewModel run unmodified on phone, tablet, tvOS, and Android TV — only the Views layer changes per form factor.

01

Config — where your Project ID lives

one value in, everything else derived

projectId is the only thing you set. clientId is a computed property that just returns it — for Descope's Generic OIDC Application, they're documented to be the same value, so there's nothing to keep in sync by hand.

Models — the shapes of the two HTTP calls

plain data, no behavior

DeviceAuthorizationResponse is what the start call returns (device_code, user_code, verification_uri…). DeviceTokenResponse is a success from the poll. DeviceFlowPollError enumerates the four RFC 8628 poll states — authorization_pending, slow_down, access_denied, expired_token — as an actual type instead of loose strings.

03

Service — the only place that touches the network

two functions, one per HTTP call

startDeviceAuthorization() makes the start call once. pollForToken(deviceCode:) makes one poll and returns a result the caller interprets — it doesn't loop itself. That choice matters: it means the polling policy (how often, when to back off, when to give up) lives entirely in the ViewModel, not buried inside the network layer.

DeviceAuthService.swiftSwift
enum PollResult {
    case success(DeviceTokenResponse)
    case pending(DeviceFlowPollError)         // authorization_pending / slow_down
    case terminalFailure(DeviceFlowPollError) // access_denied / expired_token
}

3

The state machine

DeviceAuthViewModel.State has five cases, and every screen in the app is just a direct rendering of one of them — there's no separate "loading" boolean or hidden UI state to lose track of. 

stateDiagram-v2
    [*] --> signedOut
    signedOut --> startingFlow: startSignIn()
    startingFlow --> awaitingApproval: device_code received
    startingFlow --> error: start call failed
    awaitingApproval --> awaitingApproval: poll → authorization_pending
    awaitingApproval --> signedIn: poll → success
    awaitingApproval --> error: access_denied / expired_token
    awaitingApproval --> signedOut: cancelSignIn()
    signedIn --> signedOut: signOut()
    error --> startingFlow: startSignIn() (retry)
.awaitingApproval(_, secondsRemaining:)

Two Tasks (Swift) / coroutines (Kotlin) run at once here: one polls the token endpoint on the server-given interval; the other just ticks secondsRemaining down every second so the countdown on screen stays live. Cancelling either — sign out, back out of the screen — cancels both.

.signedIn(token, claims)

claims comes from decoding the ID token's JWT payload locally, purely for display — the signature is never verified. That's fine for showing "who's signed in" in a demo; a real app needs to verify against the project's JWKS before trusting anything in it.

Why slow_down gets special treatment

Every other poll outcome is terminal or unchanged. slow_down is the one case that mutates the loop's own pacing — intervalSeconds += 5 — because RFC 8628 requires backing off when the server asks, or Descope can start rejecting the polls outright.

4

Same core, four form factors

None of the platform-specific work touches Config, Models, Service, or ViewModel. It's all in how the Views layer renders the same five states.

iOS

Touch UI, portrait-locked on iPhone.

iPadOS

Same target, same binary — content column caps at 500pt via horizontalSizeClass instead of stretching full-width.

tvOS

Separate Xcode target, same source files — #if os(tvOS) scales type/padding for a 10-foot view; SwiftUI focus handles the Siri Remote for free.

Android TV / Google TV

Same APK as the phone build — isTelevision() swaps in a tv-material screen tree with real D-pad focus rings at runtime.

5

The one thing to know before you push this

scope is deliberately empty

Both Config files request an empty OAuth scope, not openid profile email. That's a workaround, not a design choice: this project's device-authentication consent step (E108001) currently fails on any real scope, regardless of client type. Empty scope means the ID token only carries sub — no name or email. Full detail is in the root README's Troubleshooting section; nothing about it is specific to one platform.
